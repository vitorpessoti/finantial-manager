# Finantial Manager

A personal finance manager built to track income and expenses. The project was designed with a decoupled architecture using a message queue, where transactions are not persisted immediately — instead, they are published to a RabbitMQ queue and processed by a separate consumer service.

---

## Architecture

The system is composed of three services:

```
┌────────────────────────┐        ┌────────────────────┐        ┌──────────────────────────────┐
│                        │        │                    │        │                              │
│  finantial-dashboard   │◄──────►│   transactions-    │───────►│          RabbitMQ            │
│  (Angular)             │        │   service (API)    │        │                              │
│                        │        │                    │        │  • pending_transactions      │
└────────────────────────┘        └────────────────────┘        │  • update_transactions       │
                                                                │  • processed_transactions    │
                                                                │  • updated_processed_        │
                                                                │    transactions              │
                                                                └──────────────┬───────────────┘
                                                                               │
                                                                               ▼
                                                                ┌──────────────────────────────┐
                                                                │                              │
                                                                │   transaction-processing-    │
                                                                │   service (Consumer)         │
                                                                │                              │
                                                                └──────────────┬───────────────┘
                                                                               │
                                                                               ▼
                                                                ┌──────────────────────────────┐
                                                                │                              │
                                                                │         PostgreSQL           │
                                                                │                              │
                                                                └──────────────────────────────┘
```

**transactions-service** — REST API responsible for authentication, transaction creation, and publishing messages to RabbitMQ queues.

**transaction-processing-service** — Consumer service that listens to RabbitMQ queues and persists transactions to PostgreSQL.

**finantial-dashboard** — Angular frontend for interacting with the API.

---

## Key Design Decisions

**Why a message queue instead of persisting directly?**

The API and the persistence layer are intentionally decoupled. Publishing to a queue instead of writing directly to the database means that if the consumer service or the database goes down, no transaction is lost — messages stay in the queue until they are successfully processed.

**ACK only after successful persistence**

The consumer only acknowledges (`ack`) a message after it has been successfully saved to the database. If the consumer crashes mid-processing, the message remains in the queue and will be reprocessed.

**User-provided transaction date**

Transactions accept a date field provided by the user, decoupling the moment of registration from when the transaction actually occurred. This allows retroactive entries — for example, registering a past expense from a receipt.

**Mandatory Two-Factor Authentication (2FA)**

Login requires a TOTP (Time-based One-Time Password) code generated by an authenticator app (Google Authenticator, Authy, etc.). On registration, the user receives a QR Code to set up the authenticator. The `speakeasy` library handles secret generation and token validation.

## Getting Started

### Prerequisites

- [Docker Desktop](https://www.docker.com/products/docker-desktop/)

### Setup

**1. Clone the repository**

```bash
git clone https://github.com/vitorpessoti/finantial-manager.git
cd finantial-manager
```

**2. Configure environment variables**

Copy the example env files and fill in the values:

```bash
cp transactions-service/.env.example transactions-service/.env
cp transaction-processing-service/.env.example transaction-processing-service/.env
```

**3. Start all services**

```bash
docker compose up --build
```

This will start:
- PostgreSQL on port `5432`
- RabbitMQ on port `5672` (management UI on `15672`)
- transactions-service on port `3000`
- transaction-processing-service on port `3001`
- finantial-dashboard on port `4200`

**4. Run database migrations**

```bash
docker compose exec transactions-service npx prisma migrate deploy
```

**5. Start the queue listeners**

After all services are up, start the RabbitMQ listeners on the consumer service:

```bash
# Start listener for new transactions
POST http://localhost:3001/queue-consumer/new-transactions/start-listener

# Start listener for transaction updates
POST http://localhost:3001/queue-consumer/update-transactions/start-listener
```

**6. Access the application**

Open `http://localhost:4200` in your browser.

## API Reference

### Auth — `transactions-service` (port 3000)

| Method | Endpoint | Description |
|---|---|---|
| POST | `/auth/register` | Register a new user and receive a 2FA QR Code |
| POST | `/auth/2fa/verify` | Verify the 2FA token from the authenticator app |
| POST | `/auth/2fa/login` | Login with credentials and 2FA token |
| POST | `/auth/logout` | Logout |

### Transactions — `transactions-service` (port 3000)

| Method | Endpoint | Description |
|---|---|---|
| POST | `/transactions` | Create a transaction and publish it to the pending queue |
| GET | `/transactions/:id` | Get a persisted transaction by ID |
| GET | `/transactions/users/:id` | Get all persisted transactions for a user |
| PATCH | `/transactions/:id` | Update a transaction and publish it to the update queue |
| POST | `/transactions/pending/process` | Process pending transactions from both queues |
